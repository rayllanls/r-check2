**Researched:** 2026-04-01

**Confidence:** HIGH

## Summary

Phase 4 wires an existing, partially-built AI layer into the live scan pipeline. The
`GroqAIClient` and `Finding.ai_explanation` / `Finding.ai_fix_suggestion` fields already
exist — the phase is about connecting them: loading the token at scan time, running
enrichment asynchronously after the scan completes (without blocking the GUI or the HTML
report), displaying results in the modal, and rendering them conditionally in the HTML
template.

The single blocking risk identified during research is the Groq model ID stored in
`app/config.py`. `llama-3.1-70b-versatile` was deprecated January 24 2025 and is no
longer callable. The config must be updated to `llama-3.3-70b-versatile` (or the lighter
`llama-3.1-8b-instant`) before any live calls can work.

The existing threading architecture (daemon `Thread` + `root.after()` polling) is exactly
the right pattern for async AI enrichment — no new concurrency primitive is needed.

**Primary recommendation:** Add an `AIEnricher` service that runs in a daemon thread after
scan completion, populates `finding.ai_explanation` and `finding.ai_fix_suggestion` in
place on the top-10 Critical/High findings, and schedules GUI refresh via
`widget.after(0, callback)`. The HTML report already receives the `ScanResult` object;
once fields are populated, a Jinja2 conditional block renders them automatically.

### Pattern 1: Post-scan AI Enrichment (daemon thread)

**What:** After `ScanOrchestrator.scan()` returns a `ScanResult`, `AIEnricher.enrich_async()` is called. It spawns a daemon thread that iterates the top-10 Critical/High findings, calls `GroqAIClient` for each, mutates `finding.ai_explanation` and `finding.ai_fix_suggestion` in place, then calls `on_progress(finding)` and `on_complete()` callbacks — both scheduled via `widget.after(0, ...)` to reach the Tkinter thread safely.

**When to use:** Any time a scan completes and a token is configured. Called from `ResultsScreen.on_show()` or from the `ProgressScreen` scan completion handler, after the `ScanResult` is available.

**Example:**
```python
# app/ai/enricher.py
import threading
from typing import Callable, Optional
from app.ai.groq_client import GroqAIClient
from app.core.models import Finding, ScanResult, Severity

_TOP_N = 10
_HIGH_SEVERITIES = {Severity.CRITICAL, Severity.HIGH}


class AIEnricher:
    """Enriches top-N Critical/High findings with AI explanations.
    
    Runs in a daemon thread. Never blocks the caller.
    Silent fallback when token is absent or Groq call fails.
    """

    def __init__(self, token: str) -> None:
        self._token = token.strip() if token else ""

    def enrich_async(
        self,
        result: ScanResult,
        on_finding_enriched: Optional[Callable[[Finding], None]] = None,
        on_complete: Optional[Callable[[], None]] = None,
    ) -> None:
        """Spawn daemon thread. Returns immediately."""
        if not self._token:
            if on_complete:
                on_complete()
            return
        t = threading.Thread(
            target=self._run,
            args=(result, on_finding_enriched, on_complete),
            daemon=True,
        )
        t.start()

    def _run(self, result, on_finding_enriched, on_complete):
        try:
            client = GroqAIClient(self._token)
        except ValueError:
            if on_complete:
                on_complete()
            return

        candidates = [
            f for f in result.findings
            if f.severity in _HIGH_SEVERITIES
        ][:_TOP_N]

        for finding in candidates:
            try:
                finding.ai_explanation = client.explain_finding(finding)
                finding.ai_fix_suggestion = client.suggest_fix(finding)
            except Exception:
                pass  # silent fallback per AI-04
            if on_finding_enriched:
                on_finding_enriched(finding)

        if on_complete:
            on_complete()
```

### Pattern 2: Token Loading at Enrichment Time

**What:** Read token from `~/.secscan/config.json` at the moment enrichment starts, not at app startup. This means a token saved in Settings and immediately running another scan uses the new token without restart.

**Where to read it:** In the component that calls `AIEnricher` (either `ProgressScreen` scan completion handler or `ResultsScreen.on_show()`). Use the same `json.loads(CONFIG_FILE.read_text())` pattern already in `SettingsScreen._load_token()`.

```python
# Token loading helper (add to app/config.py or inline in enricher caller)
def load_groq_token() -> str:
    """Read Groq token from ~/.secscan/config.json. Returns '' if absent."""
    try:
        if CONFIG_FILE.exists():
            return json.loads(CONFIG_FILE.read_text()).get("groq_token", "")
    except (json.JSONDecodeError, OSError):
        pass
    return ""
```

### Pattern 3: GUI Update from AI Enrichment Thread

**What:** AI enrichment runs in a daemon thread. To update `FindingDetailModal` labels when enrichment completes, use `widget.after(0, callback)` — same pattern as `_open_report()` in `results_screen.py`.

**Critical rule:** Never call `.configure()` on a CTkWidget from a non-main thread. Always schedule via `.after(0, ...)`.

```python
# In ResultsScreen.on_show() — trigger enrichment after scan result arrives
def on_show(self, scan_result=None, **kwargs):
    # ... existing rendering logic ...
    token = load_groq_token()
    if token:
        enricher = AIEnricher(token)
        enricher.enrich_async(
            scan_result,
            on_finding_enriched=lambda f: self.after(0, lambda: self._on_finding_enriched(f)),
            on_complete=lambda: self.after(0, self._on_ai_complete),
        )
```

### Pattern 4: FindingDetailModal AI Section

**What:** `FindingDetailModal` already shows title, file:line, snippet, description. Add a new section below description for AI content. If `finding.ai_explanation` is `None` at open time, show a "Carregando explicacao IA..." placeholder. The modal can expose a method `update_ai_content(finding)` that the screen calls via `.after(0, ...)` when enrichment arrives.

**Complication:** The modal may already be closed by the time enrichment finishes. Guard against this with `winfo_exists()` before calling `.configure()`.

```python
# In FindingDetailModal
def update_ai_content(self, finding) -> None:
    """Call from main thread after AI enrichment completes for this finding."""
    if not self.winfo_exists():
        return
    if finding.ai_explanation:
        self._ai_explanation_box.configure(state="normal")
        self._ai_explanation_box.delete("1.0", "end")
        self._ai_explanation_box.insert("end", finding.ai_explanation)
        self._ai_explanation_box.configure(state="disabled")
    if finding.ai_fix_suggestion:
        self._ai_fix_box.configure(state="normal")
        self._ai_fix_box.delete("1.0", "end")
        self._ai_fix_box.insert("end", finding.ai_fix_suggestion)
        self._ai_fix_box.configure(state="disabled")
```

### Pattern 5: Conditional AI Block in report.html

**What:** The Jinja2 template already accesses `finding.ai_explanation` and `finding.ai_fix_suggestion` (they are dataclass fields, so Jinja2 can access them as attributes). Add a conditional block inside each finding row.

**When enrichment runs asynchronously:** The HTML report is generated immediately after scan by `_open_report()` in `results_screen.py`. If AI enrichment hasn't completed yet, `ai_explanation` will be `None` and the block won't render — that's correct per the success criteria ("HTML report opens immediately, AI content populates asynchronously").

**Important:** There are two separate moments the report can be generated:
1. Immediately on "Ver Relatório Completo" click (AI may still be running → fields may be None)
2. If the user re-generates the report after enrichment completes → fields will be populated

This is acceptable per the success criteria. No special handling needed; the Jinja2 conditional handles both cases.

```html

<tr style="border-bottom:none;background:transparent">
```

### Pattern 6: `suggest_fix()` method for GroqAIClient

The existing `explain_finding()` covers explanation only. AI-03 requires a separate fix suggestion. Two options:

**Option A — Two separate calls (simpler, higher RPM cost):**
```python
def suggest_fix(self, finding: Finding) -> str:
    """Returns a concrete fix suggestion. Returns '' on failure."""
    prompt = (
        f"Você é um especialista em segurança. Dê uma sugestão de correção concreta "
        f"para um dev iniciante.\n\n"
        f"Vulnerabilidade: {finding.title}\n"
        f"Arquivo: {finding.file_path} (linha {finding.line_number})\n"
        f"Código vulnerável:\n{finding.snippet}\n\n"
        f"Forneça: 1) O código corrigido 2) Explicação em 1-2 frases do que mudou. "
        f"Seja direto, máximo 300 tokens."
    )
    try:
        r = httpx.post(
            GROQ_API_URL,
            headers={"Authorization": f"Bearer {self._token}"},
            json={
                "model": GROQ_MODEL,
                "messages": [{"role": "user", "content": prompt}],
                "max_tokens": 400,
                "temperature": 0.2,
            },
            timeout=NETWORK_TIMEOUT_GROQ,
        )
        if r.status_code == 200:
            return r.json()["choices"][0]["message"]["content"]
    except Exception:
        pass
    return ""
```

**Option B — Combined single call (halves RPM cost, recommended for free tier):**
Ask the model for both in one JSON-structured response. More complex parsing but uses only 1 of the 30 RPM budget per finding instead of 2.

**Recommendation: Option A for Phase 4.** The RPM limit is 30/min; with max 10 findings that's 20 calls, well within the 30 RPM limit. Option B optimization can be done in Phase 5 if rate limiting becomes a practical problem.

### Anti-Patterns to Avoid

- **Calling AI from the Tkinter main thread:** Will freeze the GUI for 15s per finding (NETWORK_TIMEOUT_GROQ). Always use a daemon thread.
- **Blocking report generation on AI completion:** HTML report must open immediately. Never wait for AI enrichment before calling `generate_report()`.
- **Raising/showing errors on 401 (invalid token):** httpx returns 401 for bad tokens. The current `groq_client.py` silently returns `""` on any non-200. This is correct behavior per AI-04 — do not add error dialogs.
- **Using `check=True` in subprocesses:** Not directly relevant to AI, but the project-wide rule applies. Not needed here since no subprocess calls are made.
- **Mutating ScanResult.findings after report is written:** The report is written to a temp file; mutations to in-memory `Finding` objects after that point don't update the already-written HTML file. This is expected and acceptable.

## Common Pitfalls

### Pitfall 1: Deprecated Model ID
**What goes wrong:** All Groq API calls return 404/400 because `llama-3.1-70b-versatile` was removed January 24 2025.
**Why it happens:** The model ID is hardcoded in `app/config.py` using the old name from initial design.
**How to avoid:** First task of Wave 0: change `GROQ_MODEL` to `"llama-3.1-8b-instant"` (recommended) or `"llama-3.3-70b-versatile"`.
**Warning signs:** `r.status_code` is 400 or 404; `r.json()` contains `"model_not_found"` or similar.

### Pitfall 2: Rate Limit Exhaustion on Free Tier
**What goes wrong:** After 1,000 requests/day (llama-3.3-70b) or 30 requests/minute, Groq returns HTTP 429. Findings fail silently.
**Why it happens:** Each finding requires 2 API calls (explain + fix). 10 findings = 20 calls. If the dev runs 50+ scans/day, they hit the 1K RPD limit on 70B.
**How to avoid:** Default to `llama-3.1-8b-instant` (14,400 RPD). Document this in settings UI.
**Warning signs:** `r.status_code == 429`. The current silent `""` return handles this correctly — no user-visible error.

### Pitfall 3: FindingDetailModal Already Closed When AI Arrives
**What goes wrong:** `widget.after(0, lambda: modal.update_ai_content(f))` is scheduled but the modal was already closed by the user. Tkinter raises `TclError: invalid command name`.
**Why it happens:** Modals are destroyed when closed, but callbacks scheduled via `.after()` still fire.
**How to avoid:** Always guard with `if self.winfo_exists(): return` at the top of any deferred callback on a Toplevel.
**Warning signs:** `TclError` in stderr during testing.

### Pitfall 4: AI Enrichment Fires Before `on_show()` Completes
**What goes wrong:** `enrich_async()` is called in `on_show()`, which runs on the Tkinter main thread. The daemon thread starts immediately and may call `on_finding_enriched` before `on_show()` finishes building the modal registry.
**Why it happens:** Daemon threads start instantly.
**How to avoid:** Only register modals for AI updates after `on_show()` fully completes. Use `self.after(0, lambda: enricher.enrich_async(...))` to defer enrichment start by one event loop cycle.

### Pitfall 5: report.html Jinja2 `sort` Filter and Enum Comparison
**What goes wrong:** The template uses `{% for f in result.findings | sort(attribute="severity") %}`. `Severity` is a `str` enum; Jinja2's `sort` compares string values alphabetically ("critical" < "high" < "info" < "low" < "medium") which is NOT the desired order.
**Why it happens:** Generator.py already pre-sorts before passing to template (see `sorted_result`). The template's `sort` is redundant and wrong.
**How to avoid:** Remove the `sort` filter from the template loop (use pre-sorted findings from `generator.py`). This is a pre-existing issue; Phase 4's AI template additions should not re-introduce the filter.

### Pitfall 6: Calling `generate_report()` Twice
**What goes wrong:** To show AI content in the report, one approach is to regenerate the HTML after enrichment completes. This causes the browser tab to reload or display an outdated cached version.
**Why it happens:** `generate_report()` writes to the same temp path every time.
**How to avoid:** Do not regenerate the report after enrichment. The success criteria explicitly states "HTML report opens immediately" — AI content in the report is a best-effort feature for findings where enrichment has already completed. Users who want AI in their report can click "Ver Relatório Completo" again after enrichment finishes (within the session).

## Open Questions

1. **Should AI enrichment start in `ProgressScreen` (on scan complete event) or in `ResultsScreen.on_show()`?**
   - What we know: Scan completes in `ProgressScreen`, which then navigates to `ResultsScreen`. Starting enrichment in `ProgressScreen` means more time elapses before the user sees results. Starting in `ResultsScreen.on_show()` is simpler and keeps AI concerns out of the progress screen.
   - Recommendation: Start enrichment in `ResultsScreen.on_show()` — cleaner separation.

2. **Should `FindingDetailModal` show a loading indicator for AI content?**
   - What we know: If a user clicks a finding immediately after scan, AI enrichment may not have completed. The modal can show "Carregando..." or simply show nothing.
   - Recommendation: Show "Buscando explicação IA..." placeholder that gets replaced when enrichment arrives. This is better UX than an empty box. Use a `CTkLabel` that gets replaced/hidden once content arrives.

3. **Re-generate report after enrichment to include AI content?**
   - What we know: The success criteria says "HTML report opens immediately, AI content populates asynchronously." This implies the report is the immediate version (no AI), not a later version.
   - Recommendation: Do not re-generate. The report captures the point-in-time state. Users who want AI in the PDF should wait for the enrichment status indicator (to be added in Phase 5 polish) before exporting. This simplifies Phase 4 significantly.
