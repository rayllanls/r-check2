# Phase 03.1: Trivy Scanner Backend — Research

**Researched:** 2026-04-01
**Domain:** Trivy CLI integration — SCA (dependency vulnerabilities), IaC misconfiguration, secrets detection
**Confidence:** HIGH

---

## Summary

Trivy v0.69.3 is a multi-purpose security scanner from Aqua Security. A single `trivy fs` command can simultaneously detect dependency vulnerabilities (SCA), IaC misconfigurations (Dockerfile, Terraform, K8s, Helm), and secrets — making it a powerful complement to Grype, which covers CVEs but not IaC or misconfigs.

The integration pattern is nearly identical to Grype: subclass `BaseTool`, call `resolve_binary()`, run `trivy fs --format json --output -` (or stdout), parse the `Results` array, and normalize each finding type into a `Finding` object. The key difference is that Trivy's JSON envelope contains three distinct sub-arrays per result (`Vulnerabilities`, `Misconfigurations`, `Secrets`), each with different field names — so normalization requires three separate `_normalize_*()` methods.

The one significant operational constraint is Trivy's vulnerability database: the first run downloads a ~55 MB OCI-packaged DB to `~/.cache/trivy/`. Subsequent runs reuse the cache (refreshed every 12 hours). This is a one-time setup cost per machine, not a per-scan penalty. For `misconfig` and `secret` scanning only, the embedded checks bundle ships inside the binary and requires no network access.

**Primary recommendation:** Implement `TrivyTool` as a `BaseTool` subclass running `trivy fs --scanners vuln,misconfig,secret --format json` on the target directory. Add `trivy` to `PLAN_TOOLS["team"]` in `config.py`, replacing the placeholder `checkov` entry. Use three `_normalize_*()` helpers for the three finding types, mapping all Trivy severities (UPPERCASE) to the project's `Severity` enum.

### Pattern 1: TrivyTool Class Structure

```python
# Source: grype.py (project reference implementation)
class TrivyTool(BaseTool):
    tool_name = "trivy"

    def run(self, project_path: Path) -> list[Finding]:
        binary = self.resolve_binary()
        cmd = [
            binary, "fs",
            "--scanners", "vuln,misconfig,secret",
            "--format", "json",
            "--quiet",          # suppress progress bars in subprocess
            str(project_path),
        ]
        result = subprocess.run(
            cmd, capture_output=True, text=True, timeout=300
        )
        # Trivy exits non-zero when findings exist — do NOT use check=True

        if not result.stdout or not result.stdout.strip():
            return []
        try:
            raw = json.loads(result.stdout)
        except json.JSONDecodeError:
            return []

        findings = []
        for result_block in raw.get("Results", []):
            target = result_block.get("Target", "")
            findings.extend(self._parse_vulns(result_block, target))
            findings.extend(self._parse_misconfs(result_block, target))
            findings.extend(self._parse_secrets(result_block, target))
        return findings
```

### Pattern 2: Three Normalization Helpers

**Vulnerabilities** (Class: `lang-pkgs`, `os-pkgs`):
```python
# Source: integration/testdata/alpine-39.json.golden (GitHub)
def _parse_vulns(self, block: dict, target: str) -> list[Finding]:
    findings = []
    for v in block.get("Vulnerabilities", []):
        vuln_id = v.get("VulnerabilityID", "unknown")
        pkg_name = v.get("PkgName", "unknown")
        installed = v.get("InstalledVersion", "unknown")
        fixed = v.get("FixedVersion", "")
        fix_text = f" Fix in: {fixed}" if fixed else " No fix available."
        findings.append(Finding(
            id=str(uuid.uuid4()),
            title=f"{vuln_id}: {pkg_name} {installed}",
            severity=SEVERITY_MAP.get(v.get("Severity", "UNKNOWN"), Severity.INFO),
            category=FindingCategory.DEPENDENCY,
            file_path=target,
            line_number=0,
            snippet=f"{pkg_name}=={installed}",
            description=f"{v.get('Title', v.get('Description', ''))}.{fix_text}",
            tool="trivy",
            rule_id=vuln_id,
        ))
    return findings
```

**Misconfigurations** (Class: `config`; only `Status == "FAIL"`):
```python
# Source: integration/testdata/dockerfile.json.golden + terraform-remote-module.json.golden (GitHub)
def _parse_misconfs(self, block: dict, target: str) -> list[Finding]:
    findings = []
    for m in block.get("Misconfigurations", []):
        if m.get("Status") != "FAIL":
            continue
        cause = m.get("CauseMetadata", {})
        line_number = cause.get("StartLine", 0) or 0
        findings.append(Finding(
            id=str(uuid.uuid4()),
            title=f"{m.get('ID', 'unknown')}: {m.get('Title', '')}",
            severity=SEVERITY_MAP.get(m.get("Severity", "UNKNOWN"), Severity.INFO),
            category=FindingCategory.IAC,
            file_path=target,
            line_number=line_number,
            snippet=m.get("Message", ""),
            description=f"{m.get('Description', '')} Resolution: {m.get('Resolution', '')}",
            tool="trivy",
            rule_id=m.get("ID", ""),
        ))
    return findings
```

**Secrets** (Class: `secret`):
```python
# Source: integration/testdata/secrets.json.golden (GitHub)
def _parse_secrets(self, block: dict, target: str) -> list[Finding]:
    findings = []
    for s in block.get("Secrets", []):
        findings.append(Finding(
            id=str(uuid.uuid4()),
            title=f"Secret detected: {s.get('Title', s.get('RuleID', 'unknown'))}",
            severity=SEVERITY_MAP.get(s.get("Severity", "HIGH"), Severity.HIGH),
            category=FindingCategory.SECRET,
            file_path=target,
            line_number=s.get("StartLine", 0) or 0,
            snippet=s.get("Match", ""),
            description=f"Trivy found a {s.get('Category', 'unknown')} secret matching rule '{s.get('RuleID', '')}'",
            tool="trivy",
            rule_id=s.get("RuleID", ""),
        ))
    return findings
```

### Anti-Patterns to Avoid

- **Filtering by `Class` field:** Do not pre-filter `Results` blocks by `Class` before normalizing. Instead, attempt all three `_parse_*()` calls on every block — blocks that don't contain the relevant sub-array simply return empty lists. This is simpler and future-proof.
- **Using `check=True`:** Trivy exits with code 1 when findings exist (same as Semgrep/Grype). Never add `check=True` to the subprocess call.
- **Running `trivy config` separately:** `trivy fs --scanners vuln,misconfig,secret` covers all three in one subprocess call. No need for a separate `trivy config` subcommand.
- **Skipping `--quiet` flag:** Without `--quiet`, Trivy emits progress bars and log lines to stdout/stderr that can corrupt JSON parsing.

## Common Pitfalls

### Pitfall 1: Vulnerability DB Not Downloaded on First Run
**What goes wrong:** `trivy fs --scanners vuln,...` fails with "database error: --skip-update cannot be specified on the first run" or silently returns 0 vulnerabilities because the DB doesn't exist.
**Why it happens:** Trivy's vulnerability database is a separate ~55 MB OCI artifact stored in `~/.cache/trivy/db/`. It must be downloaded before the first vulnerability scan.
**How to avoid:** Add a `trivy image --download-db-only` setup step in docs/onboarding. At runtime, if the DB is absent, catch the error and emit a `TOOL_ERROR` event with a user-friendly message: "Trivy requires a one-time DB download (~55 MB). Run: trivy image --download-db-only".
**Warning signs:** Empty `Vulnerabilities` arrays in results despite a project with known-vulnerable dependencies.

### Pitfall 2: `--quiet` Missing — JSON Corrupted by Progress Output
**What goes wrong:** `json.JSONDecodeError` when parsing `result.stdout` because Trivy writes progress/log lines to stdout before the JSON blob.
**Why it happens:** By default, Trivy emits scanning progress to stdout. On some versions, this intermingles with JSON output.
**How to avoid:** Always pass `--quiet` flag. Use `capture_output=True` which captures stderr separately. Verify output starts with `{` before parsing.
**Warning signs:** `JSONDecodeError` with truncated JSON containing "scanning" or "INFO" text at the start.

### Pitfall 3: Misconfigurations Include `PASS` Status — Creates False Findings
**What goes wrong:** Every file checked generates findings even when it passes all checks.
**Why it happens:** Trivy includes both `FAIL` and `PASS` status entries in the `Misconfigurations` array.
**How to avoid:** Filter strictly: `if m.get("Status") != "FAIL": continue` in `_parse_misconfs()`.
**Warning signs:** Massive finding counts from a clean project.

### Pitfall 4: `CauseMetadata.StartLine` is Optional / 0
**What goes wrong:** `line_number` is `None` or causes `TypeError` in downstream code expecting `int`.
**Why it happens:** Some misconfigurations (e.g., absence-based checks like "no USER in Dockerfile") have no specific line to point to. `StartLine` may be absent or `0`.
**How to avoid:** Use `cause.get("StartLine", 0) or 0` — the `or 0` handles `None` returns. The `Finding.line_number` field accepts `0` as "no specific line".
**Warning signs:** `TypeError: unsupported operand type(s) for +: 'NoneType' and 'int'`.

### Pitfall 5: Grype and Trivy Duplicate SCA Findings
**What goes wrong:** The same CVE (e.g., CVE-2023-30861 in Flask) appears twice in results — once from Grype, once from Trivy.
**Why it happens:** Both tools scan dependency manifests for known CVEs. Their databases overlap significantly.
**How to avoid:** The `tool` field on `Finding` distinguishes the source. Deduplication is a Phase 5 polish concern, not Phase 03.1. For now, accept duplicates — they're labeled by tool. Document this in code comments.
**Warning signs:** Users complain about "double" CVE findings.

### Pitfall 6: `--scanners` Flag Behavior Differences by Subcommand
**What goes wrong:** `trivy fs` with `--scanners misconfig` scans IaC but not vuln. `trivy config` only does IaC. Mixing up subcommands leads to incomplete coverage.
**Why it happens:** Each Trivy subcommand has different default scanners.
**How to avoid:** Use `trivy fs --scanners vuln,misconfig,secret` explicitly. Never rely on defaults.
**Warning signs:** Missing vulnerability findings when only `trivy config` is called.

## Trivy JSON Schema Reference

### Top-Level Envelope
```json
{
  "SchemaVersion": 2,
  "ArtifactName": "/path/to/scanned/dir",
  "ArtifactType": "filesystem",
  "Results": [ ]
}
```

### Results Block
```json
{
  "Target": "path/to/file",
  "Class": "lang-pkgs | os-pkgs | config | secret",
  "Type": "python | terraform | dockerfile | ...",
  "Vulnerabilities": [],
  "Misconfigurations": [],
  "Secrets": []
}
```
Note: `Target` is the file path relative to the scanned directory. Use it as `file_path` in `Finding`.

### Vulnerability Object (key fields)
```json
{
  "VulnerabilityID": "CVE-2019-1549",
  "PkgName": "libcrypto1.1",
  "InstalledVersion": "1.1.1b-r1",
  "FixedVersion": "1.1.1d-r0",
  "Severity": "MEDIUM",
  "Title": "openssl: information disclosure in fork()",
  "Description": "..."
}
```

### Misconfiguration Object (key fields)
```json
{
  "ID": "DS-0002",
  "Title": "Image user should not be 'root'",
  "Description": "...",
  "Message": "Specify at least 1 USER command...",
  "Resolution": "Add 'USER <non root user name>' line...",
  "Severity": "HIGH",
  "Status": "FAIL",
  "CauseMetadata": {
    "StartLine": 5,
    "EndLine": 5
  }
}
```

### Secret Object (key fields)
```json
{
  "RuleID": "aws-access-key-id",
  "Category": "AWS",
  "Severity": "CRITICAL",
  "Title": "AWS Access Key ID",
  "StartLine": 3,
  "EndLine": 3,
  "Match": "export AWS_ACCESS_KEY_ID=********************"
}
```

## Open Questions

1. **Trivy SCA vs Grype SCA — duplicate CVE policy**
   - What we know: Both tools will find the same CVEs for the same dependencies. Findings are tagged by `tool` field.
   - What's unclear: Should Phase 03.1 add deduplication by `rule_id` + `file_path`?
   - Recommendation: Defer deduplication to Phase 5 (Polish). For Phase 03.1, accept duplicates; they're informative (different severity/description from each tool's DB).

2. **Trivy DB first-run UX**
   - What we know: First run requires ~55 MB DB download, cannot be skipped.
   - What's unclear: Should the app proactively download the DB at startup or let the first scan trigger it?
   - Recommendation: Let the first scan trigger it naturally. If Trivy fails due to missing DB, catch the `FileNotFoundError`/empty output and surface a user-friendly message. Document that DB download is a one-time setup.

3. **`--offline-scan` flag for no-internet environments**
   - What we know: `--offline-scan` prevents Trivy from calling Maven Central for Java dependency resolution.
   - What's unclear: Should TrivyTool always add `--offline-scan` to match project's offline-first philosophy?
   - Recommendation: Yes — add `--offline-scan` and `--skip-db-update` after first DB download. For Phase 03.1, omit these flags (require the DB download to work). Phase 5 can revisit for offline hardening.

### What Checkov Is

Checkov (by Bridgecrew/Palo Alto Prisma Cloud) is a Python-based IaC static analysis tool. It scans infrastructure-as-code files for security misconfigurations using 1,000+ built-in policy checks. It covers frameworks that Trivy's misconfig scanner also covers (Terraform, Dockerfile, K8s), but with a larger, more opinionated check set focused specifically on IaC — Checkov does NOT do SCA/CVE or git-secret scanning.

**Relationship to Trivy for this project:** Trivy and Checkov are complementary for IaC. Trivy uses Rego-based embedded checks (fast, binary, offline). Checkov uses Python-native checks (more IaC frameworks, more checks, Python package). Running both gives broader IaC coverage with different check IDs — the planner should add BOTH to `PLAN_TOOLS["team"]`, not replace one with the other.

**Installation:** `pip install checkov` — Checkov is a Python package, not a compiled binary. The `checkov` CLI entry point is a Python script (`#!/usr/bin/python3`) installed to `~/.local/bin/checkov` when installed via `pip install --user checkov`. Version installed and verified: **3.2.513**.

---

### CLI Invocation Pattern

```bash
checkov -d <path> --output json --compact
```

- `-d <path>`: directory to scan (recursive, auto-detects all supported IaC frameworks)
- `--output json`: emit JSON to stdout (all progress/log output suppressed — stderr is empty)
- `--compact`: omit `code_block` and `evaluations` fields from output (reduces size, not needed)
- No `--quiet` flag needed: unlike Trivy, Checkov with `--output json` emits **only JSON to stdout and nothing to stderr** (verified by live test)

**Exit codes (verified):**
- Exit 0: no IaC files found, or all checks pass
- Exit 1: one or more checks failed

**Do not use `check=True`** in subprocess — exit code 1 is normal when findings exist.

### JSON Output Schema

**Critical structural difference from all other project tools:** Checkov output is **polymorphic**:

| Condition | Output type | Shape |
|---|---|---|
| No IaC files found in directory | Single `dict` | `{"passed": 0, "failed": 0, "skipped": 0, "parsing_errors": 0, "resource_count": 0, "checkov_version": "3.2.513"}` |
| One IaC framework found (e.g., only `.tf` files) | Single `dict` | `{"check_type": "terraform", "results": {...}, "summary": {...}, "url": "..."}` |
| Multiple IaC frameworks found (e.g., `.tf` + `Dockerfile`) | `list` of `dict` | `[{"check_type": "terraform", ...}, {"check_type": "dockerfile", ...}]` |

The parser MUST handle all three shapes. The key distinguishing field is whether the top-level object is a `list` or `dict`, and whether a `dict` has a `check_type` key.

**Top-level check_type dict (single framework):**
```json
{
  "check_type": "terraform",
  "results": {
    "passed_checks": [...],
    "failed_checks": [...],
    "skipped_checks": [],
    "parsing_errors": []
```

**Failed check object (key fields — verified by live run):**

```json
  "bc_check_id": "BC_AWS_S3_19",
```

**Important verified facts:**
- `severity` field is **always `null`** in the open-source (non-Prisma Cloud API) version of Checkov. Severity metadata is only populated when using `--bc-api-key`. The parser must never rely on this field.
- `file_path` is the path relative to the scanned directory root (starts with `/`), e.g., `/main.tf` means `<project_root>/main.tf`.
- `file_line_range` is `[start_line, end_line]` (1-indexed integers). Use `file_line_range[0]` as `line_number`.
- `parsing_errors` in `results` is a list of file paths that failed to parse, not a count.
- `check_id` follows the pattern `CKV_<PROVIDER>_<N>` or `CKV2_<PROVIDER>_<N>` (e.g., `CKV_AWS_23`, `CKV2_AWS_6`, `CKV_DOCKER_4`, `CKV_K8S_8`).

### Severity Mapping Strategy

Since `severity` is always `null` in open-source Checkov, severity must be inferred from the `check_id` prefix. This is an imperfect but practical approach — the alternative is defaulting everything to `Severity.MEDIUM`, which loses information.

**Recommended approach: derive severity from check_id prefix conventions**

Checkov check IDs follow naming patterns that correlate with severity:
- `CKV2_*` checks are typically higher-severity (newer, more critical issues)
- `CKV_*` checks span the full range

Since there is no reliable programmatic way to map check_id to severity without the Prisma Cloud API, the recommended default is `Severity.MEDIUM` for all Checkov findings, with the `check_id` stored in `rule_id` so users can look up severity themselves.

**Severity mapping (verified):**
```python
# Source: live execution of checkov 3.2.513 — severity field is always None
# Strategy: default to MEDIUM; store check_id in rule_id for user reference
CHECKOV_DEFAULT_SEVERITY = Severity.MEDIUM

def _checkov_severity(check: dict) -> Severity:
    # severity is always None in OSS Checkov — use MEDIUM as safe default
    return CHECKOV_DEFAULT_SEVERITY
```

This is documented in the `CheckovTool` class docstring so future maintainers understand the limitation.

### Python-Tool vs Binary-Tool: BaseTool Adaptation

All existing tools (Grype, Semgrep, Gitleaks, Trufflehog, Trivy) are **compiled binaries**. Checkov is a **Python script entry point**. This creates two differences:

**1. Binary resolution:** The existing `resolve_binary()` in `BaseTool` works correctly for Checkov as-is. The `checkov` CLI is a script in `~/.local/bin/checkov`, and `BaseTool.resolve_binary()` already includes `~/.local/bin` in its `shutil.which()` search path (verified by reading `base.py` lines 33-40). No changes to `BaseTool` are needed.

**2. No `vendors/` copy needed:** Unlike Trivy (which is a binary downloaded to `vendors/linux/`), Checkov should NOT be copied to `vendors/`. It is a Python package — copying the entry point script without its package would fail. Instead, Checkov must be installed in the Python environment and discovered via PATH.

```python
# CheckovTool: tool_name = "checkov"
# resolve_binary() finds /home/admin/.local/bin/checkov (or system equivalent)
# No vendor directory entry needed
```

**3. PyInstaller consideration (Phase 7):** When bundling with PyInstaller, the `checkov` CLI script in `~/.local/bin/` will NOT be included automatically. Options:
- Bundle checkov as a Python module using `--collect-all checkov` in the PyInstaller spec
- Invoke checkov via `sys.executable -m checkov` pattern inside the frozen app (use `sys.executable` to get the bundled Python, then `-m checkov` to invoke the module)
- Document this as a Phase 7 concern; for Phases 1-5 (dev mode, no PyInstaller), `resolve_binary()` + PATH resolution is sufficient

**Recommendation for Phase 03.1:** Use `resolve_binary()` as-is. Add a note in `checkov.py` that Phase 7 will need `--collect-all checkov` or `sys.executable -m checkov` invocation.

### CheckovTool Class Structure

```python
# Source: grype.py (project reference implementation) + verified Checkov 3.2.513 JSON schema
class CheckovTool(BaseTool):
    """Checkov IaC static analysis scanner.

    Checkov is a Python CLI tool installed via pip. resolve_binary() finds it
    in ~/.local/bin/checkov or system PATH — no vendor/ copy needed.

    NOTE: severity is always null in OSS Checkov (no Prisma Cloud API key).
    All findings default to Severity.MEDIUM. The rule_id field carries the
    check_id (e.g., CKV_AWS_23) for user reference.

    Phase 7 PyInstaller: use --collect-all checkov OR invoke via
    sys.executable + ['-m', 'checkov'] instead of resolve_binary().
    """
    tool_name = "checkov"

    def run(self, project_path: Path) -> list[Finding]:
        binary = self.resolve_binary()
        cmd = [
            binary,
            "-d", str(project_path),
            "--output", "json",
            "--compact",
        ]
        result = subprocess.run(
            cmd, capture_output=True, text=True, timeout=300
        )
        # Exit 1 is normal when findings exist — do NOT use check=True

        if not result.stdout or not result.stdout.strip():
            return []
        try:
            raw = json.loads(result.stdout)
        except json.JSONDecodeError:
            return []

        # Normalize to list of check_type blocks regardless of input shape
        blocks = self._normalize_to_blocks(raw)
        findings = []
        for block in blocks:
            findings.extend(self._parse_failed_checks(block))
        return findings

    def _normalize_to_blocks(self, raw) -> list[dict]:
        """Handle Checkov's polymorphic output: summary dict, single block, or list."""
        if isinstance(raw, list):
            return raw  # multiple frameworks — already a list of check_type dicts
        if isinstance(raw, dict):
            if "check_type" in raw:
                return [raw]  # single framework block
            # "summary-only" dict (no IaC files found): {"passed": 0, ...}
            return []
        return []

    def _parse_failed_checks(self, block: dict) -> list[Finding]:
        check_type = block.get("check_type", "unknown")
        findings = []
        failed = block.get("results", {}).get("failed_checks", [])
        for chk in failed:
            check_id = chk.get("check_id", "unknown")
            file_path = chk.get("file_path", "")
            line_range = chk.get("file_line_range") or [0, 0]
            line_number = line_range[0] if line_range else 0
            resource = chk.get("resource", "")
            check_name = chk.get("check_name", "")
            guideline = chk.get("guideline", "")

            findings.append(Finding(
                id=str(uuid.uuid4()),
                title=f"{check_id}: {check_name}",
                severity=Severity.MEDIUM,  # OSS Checkov: severity always null
                category=FindingCategory.IAC,
                file_path=file_path,
                line_number=line_number,
                snippet=resource,
                description=(
                    f"[{check_type}] {check_name}."
                    + (f" See: {guideline}" if guideline else "")
                ),
                tool="checkov",
                rule_id=check_id,
            ))
        return findings
```

### Checkov-Specific Pitfalls

#### Pitfall C1: Polymorphic JSON Output Crashes the Parser
**What goes wrong:** `raw.get("Results", [])` (Trivy-style) raises `AttributeError` because `raw` is a `list`, not a `dict`.
**Why it happens:** Checkov outputs a `list` when multiple frameworks are detected, a `dict` when one framework is detected, and a summary `dict` when no IaC is found. Unlike every other tool in this project, the top-level type varies.
**How to avoid:** Always pass through `_normalize_to_blocks()` before iterating. Never call `.get()` directly on the raw parse result.
**Warning signs:** `AttributeError: 'list' object has no attribute 'get'` in `CheckovTool.run()`.

#### Pitfall C2: Assuming `severity` Field is Populated
**What goes wrong:** `SEVERITY_MAP.get(chk.get("severity"), Severity.MEDIUM)` silently returns `Severity.MEDIUM` for every finding because `severity` is always `null`.
**Why it happens:** Checkov's severity metadata is gated behind the Prisma Cloud API key (`--bc-api-key`). Without it, the field is always `null` in the JSON.
**How to avoid:** Do not build a severity map for Checkov. Document this explicitly. Use `Severity.MEDIUM` as a hardcoded default. Do not try to derive severity from check_id prefixes — the mapping is not documented and changes across versions.
**Warning signs:** All Checkov findings appear with `severity=INFO` or `severity=CRITICAL` due to incorrect map fallback.

#### Pitfall C3: `file_path` Includes Leading Slash — Mismatches Project Root
**What goes wrong:** `file_path` in findings is `/main.tf` instead of `main.tf`, causing the UI to display absolute-looking paths or fail path resolution.
**Why it happens:** Checkov sets `file_path` relative to the scanned directory but with a leading `/` (e.g., scanning `/tmp/project`, file `/tmp/project/infra/main.tf` → `file_path = "/infra/main.tf"`).
**How to avoid:** Strip the leading slash when normalizing: `file_path = chk.get("file_path", "").lstrip("/")`. This matches the behavior of other tools that return paths relative to the project root.
**Warning signs:** File paths in findings start with `/` and don't resolve correctly in the ResultsScreen.

#### Pitfall C4: `parsing_errors` is a List of Paths, Not an Integer
**What goes wrong:** Code doing `if block["results"]["parsing_errors"] > 0` raises `TypeError: '>' not supported between instances of 'list' and 'int'`.
**Why it happens:** In Checkov's JSON, `results.parsing_errors` is a `list` of file path strings (files that failed to parse), while `summary.parsing_errors` is an `int` count. The two fields have the same name but different types.
**How to avoid:** Use `summary.parsing_errors` (int) for reporting, `results.parsing_errors` (list) for enumerating specific files. Never compare `results.parsing_errors` to an integer.
**Warning signs:** `TypeError` when checking if there were parsing errors.

#### Pitfall C5: Slow Startup on Non-IaC Projects (~3.6s)
**What goes wrong:** Checkov takes ~3.6 seconds even when no IaC files exist. For large Python/JS projects, this is pure overhead.
**Why it happens:** Checkov is a Python package with a large import tree. Python startup + module loading costs ~2-3 seconds regardless of scan results.
**How to avoid:** This is inherent to Checkov as a Python package (vs compiled binary). Accept the overhead for now. The `ThreadPoolExecutor` runs Checkov concurrently with other tools, so it does not extend total scan time unless it's the slowest tool. If this becomes a user experience issue in Phase 5, add a pre-check: scan for IaC file extensions before invoking Checkov, and return `[]` immediately if none found.
**Warning signs:** Users on pure Python/JS projects see scan time increase by ~4 seconds.
